# 14 — CI (Continuous Integration)

## What problem it solves

Tests only help if they run. In practice they stop running:

- You're in a hurry and skip them.
- They pass locally because of a file you never committed.
- A teammate's change breaks your area and neither of you notices for a week.
- They pass on your Node 22 and fail on production's Node 20.

CI runs your test suite **on a machine that is not yours, on every push**. That's the whole
idea. Its real value is not "tests run" — it's *proof that a clean checkout of this commit
works*.

## How it works

`.github/workflows/ci.yml` runs on every push to `main` and every pull request. GitHub
gives you a fresh Ubuntu VM, you describe the steps, it reports pass or fail against the
commit.

### A clean machine is the point

The VM has none of your history: no `.env`, no globally installed anything, no file you
forgot to commit. If the workflow passes, someone cloning the repo can build it. That's
the guarantee — "works on my machine" stops being possible to say.

This catches a specific, common failure: code that works only because of an uncommitted
file. On your laptop it's there. On CI it isn't, so the build breaks immediately rather
than on someone else's first day.

### Real services, not mocks

```yaml
services:
  postgres:
    image: postgres:16
    options: >-
      --health-cmd "pg_isready -U cstracker -d cs_tracker"
      --health-interval 5s --health-timeout 5s --health-retries 10
```

The same Postgres 16 and Redis 7 as `docker-compose.yml`, started fresh per run and thrown
away after. Our integration tests need a real database (concept 13), and CI gives them one.

**The health check is not optional.** Without it, the job starts running tests the instant
the container is created — before Postgres finishes booting — and fails maybe one run in
five. Intermittent CI failures are the worst kind, because rerunning "fixes" it and people
learn to ignore red builds.

### Secrets in CI are fake

```yaml
env:
  JWT_SECRET: ci-only-secret-not-used-anywhere-else
```

This value exists only inside this job. It is **not** the production secret, deliberately:
CI logs are visible to anyone with repo read access, and on a public repo a fork's pull
request must never be able to reach anything real.

Real secrets go in **Settings → Secrets and variables → Actions** and appear as
`${{ secrets.NAME }}` — masked in logs, and never exposed to PRs from forks.

### `npm ci`, not `npm install`

```yaml
run: npm ci
```

`npm ci` installs **exactly** the lockfile and fails if `package.json` and the lockfile
disagree. `npm install` will happily resolve a newer version, which means CI tested
something slightly different from what you'll deploy. Reproducibility is the point.

### Order the steps to fail fast

```
install server → migrate → server tests → install client → lint → build
```

Migrations run before tests because the tests need the schema — and that means **CI also
proves the migrations work from an empty database on every run**, which is a free and
genuinely valuable check (concept 06).

Cheap and likely-to-fail steps go first: no reason to wait through a client build to learn
a server test failed.

### What "green" actually means

A passing CI run tells you: dependencies install from the lockfile, migrations apply to an
empty database, 73 tests pass, the client lints, and the client builds.

It does **not** tell you the app is correct — only that the things you wrote tests for
still hold. CI is a floor, not a ceiling.

## Making it required

By default CI reports status and nothing stops you merging a red build. To make it binding:

**Settings → Branches → Add branch protection rule** for `main`:
- ✅ Require status checks to pass before merging → select `test`
- ✅ Require branches to be up to date before merging

Without this, CI is advice. With it, `main` is always a commit that passed.

## Manual step: connect the repo

Not a git repo yet, so:

```bash
cd /Users/emilianobustos/coding-projects/cs-tracker
git init
git add -A
git commit -m "cs-tracker: habits, applications, events, goals, GitHub activity"
```

Then create an **empty** repo on github.com (no README, no .gitignore — you have both) and
run the two lines it shows you:

```bash
git remote add origin https://github.com/YOUR_USERNAME/cs-tracker.git
git branch -M main
git push -u origin main
```

The workflow runs on that first push. Watch it under the **Actions** tab.

Before pushing, confirm your secrets aren't going with it:

```bash
git status --short | grep -c '\.env$'    # must print 0
git check-ignore -v server/.env          # must print the matching .gitignore line
```

## Try it yourself

Once it's pushed, break something on purpose in a branch:

```bash
git checkout -b test-ci
# make a test fail
sed -i '' 's/assert.strictEqual(res.status, 201)/assert.strictEqual(res.status, 999)/' server/habits.test.js
git commit -am "deliberately break a test"
git push -u origin test-ci
```

Open the PR and watch the check go red before anyone reviews it. Then delete the branch.
